## Nhận định chính

Việc đổi từ `technical_reviews(*)` sang danh sách cột chi tiết là một cải thiện hợp lý, nhưng nó **không tự chữa** được trường hợp bảng `technical_reviews` chưa tồn tại, không ở `public`, hoặc chưa có FK về `business_cases`.[^3_2][^3_3][^3_1]
Tương tự, lỗi `404` ở `/profiles` thường khớp với nhóm lỗi `42P01 relation does not exist`, hoặc table không nằm ở schema REST đang expose.[^3_2]

```sql
select table_schema, table_name
from information_schema.tables

order by table_schema, table_name;
```

```sql
-- 2) Kiểm tra các foreign key liên quan
select
  conname,
  conrelid::regclass as from_table,
  confrelid::regclass as to_table,
  pg_get_constraintdef(oid) as definition
from pg_constraint
where contype = 'f'
  and (
    conrelid::regclass::text in ('business_cases', 'technical_reviews')
    or confrelid::regclass::text in ('business_cases', 'employees')
  )
order by conrelid::regclass::text, conname;
```

Nếu PostgREST không thấy quan hệ, nested query sẽ không embed được dữ liệu liên bảng.[^3_3][^3_1]
Nếu `profiles` không hiện trong `public`, lỗi `404/42P01` vẫn sẽ tiếp diễn dù code frontend đã bọc `try/catch`.[^3_2]

## Kết luận vận hành

Ở thời điểm này, em **chưa chốt là lỗi đã fix hoàn toàn**; em chốt rằng An đã xử lý một phần ở source code, còn bước quyết định là kiểm tra schema thật của Supabase.[^3_1][^3_2]
Ưu tiên đúng nhất bây giờ là xác minh 3 thứ: `public.profiles`, `public.technical_reviews`, và FK `business_cases -> employees` cùng `technical_reviews -> business_cases`; chỉ cần thiếu một trong các mắt xích này thì trang `/cases/[uuid]` vẫn có thể rơi về trạng thái “Không tìm thấy sự việc”.[^3_3][^3_1][^3_2]

Anh chạy 2 câu SQL trên rồi gửi lại kết quả `tables` và `foreign keys`.

Vấn đề còn lại không phải do thiếu bảng hay thiếu FK, mà rất có thể là do **PostgREST schema cache chưa được reload** sau khi các bảng/FK này được tạo hoặc sửa đổi.

## Vì sao vẫn lỗi dù bảng và FK đều đúng

Supabase dùng PostgREST để tự động sinh REST API dựa trên một bản schema cache được nạp khi khởi động hoặc khi có thông báo reload. Khi bảng mới (`profiles`, `technical_reviews`) hoặc constraint FK mới được tạo/đổi tên sau đó, PostgREST **không tự động biết** về thay đổi này cho đến khi schema cache được làm mới, dẫn đến lỗi `404` (bảng "không tồn tại" theo góc nhìn của API) hoặc `400` (không thể resolve relationship để embed) dù bảng thực sự đã có trong Postgres.[^4_1][^4_2]

Điều thú vị là trong sidebar SQL Editor của anh đã có sẵn một query đã lưu tên **"Reload schema via notification"** — đây chính xác là công cụ để xử lý tình huống này.[^4_3]

## Hành động cần làm ngay

Chạy lệnh sau trong SQL Editor để buộc PostgREST nạp lại schema cache:

```sql
NOTIFY pgrst, 'reload schema';
```

Sau đó thực hiện các bước kiểm tra sau:

- Đợi khoảng 5-10 giây để cache được nạp lại trên toàn bộ API instance
- Hard refresh trình duyệt (Ctrl+Shift+R) để xóa cache phía client
- Load lại trang `/cases/[uuid]` và kiểm tra Console có còn lỗi `400`/`404` không


## Vấn đề phụ cần xử lý — bảng `profiles` còn trống

Ngay cả khi cache được reload, bảng `profiles` hiện tại nhiều khả năng **chưa có dòng dữ liệu nào** cho user `df33230a-600a-4885-a37b-37f64a3d341a`, nên dù API hoạt động đúng thì query vẫn trả `null` (do dùng `maybeSingle()`), khiến `currentUserRole` fallback về `'sales'`. Anh chạy tiếp:

```sql
INSERT INTO public.profiles (id, role) 
VALUES ('df33230a-600a-4885-a37b-37f64a3d341a', 'pe') 
ON CONFLICT (id) DO UPDATE SET role = 'pe';
```


## Về khóa ngoại `technical_reviews_approved_by_fkey`

Đáng lưu ý là cột `approved_by` trong `technical_reviews` đang tham chiếu tới `auth.users(id)` chứ không phải `employees(employee_id)`, khác với `requested_by` và `reviewed_by` đều tham chiếu `employees`. Đây không gây lỗi ngay bây giờ vì code hiện tại chỉ select cột này (không embed), nhưng nếu sau này An muốn hiển thị tên người phê duyệt (approved_by) bằng join, sẽ cần thêm bước join riêng qua `auth.users` hoặc đổi thiết kế để trỏ về `employees` cho nhất quán.

Anh chạy 2 lệnh SQL trên rồi thử lại trang chi tiết case, báo lại kết quả console log nhé.

Vẫn lỗi

Đã xác định: **không còn là lỗi thiếu bảng, FK hay schema cache**. Query đang yêu cầu ít nhất một **tên cột không tồn tại hoặc sai tên** trong `technical_reviews`; vì chỉ một cột sai là toàn bộ query `business_cases` trả HTTP 400, khiến UI hiển thị “Không tìm thấy sự việc”. HTTP 400 của PostgREST thường phản ánh request/schema không khớp; phải đọc phần body lỗi để biết chính xác cột nào.[^5_1][^5_2]

## Vì sao chắc chắn

Bảng `technical_reviews`, `profiles`, `business_cases`, `employees` đều hiện hữu trong `public`; đồng thời FK `technical_reviews_case_id_fkey` và `business_cases_sales_owner_id_fkey` cũng có đầy đủ theo kết quả SQL anh gửi.[^5_3]
Trong query bị lỗi, phần đáng nghi nhất là danh sách 25 cột của `technical_reviews`, đặc biệt: `version`, `approval_status`, `mold_option`, `cutting_die_option`, `cycle_time_sec`, `technical_constraints`, `rejected_reason` — chỉ cần khác một ký tự so với schema thật là request bị từ chối.

## Kiểm tra chính xác cột sai

Chạy SQL này để lấy cấu trúc thực tế của bảng:

```sql
select
  ordinal_position,
  column_name,
  data_type,
  is_nullable
from information_schema.columns
where table_schema = 'public'
  and table_name = 'technical_reviews'
order by ordinal_position;
```

Sau đó chạy phép đối chiếu tự động — nó sẽ trả về **những cột code đang gọi nhưng DB không có**:

```sql
with expected(column_name) as (
  values
    ('id'), ('case_id'), ('version'), ('approval_status'),
    ('product_id'), ('design_revision_id'), ('material_spec'),
    ('thickness_mm'), ('special_requirements'), ('mold_option'),
    ('mold_id'), ('pocket_count'), ('cutting_die_option'),
    ('cutting_die_id'), ('machine_id'), ('lead_time_days'),
    ('cycle_time_sec'), ('technical_constraints'), ('rejected_reason'),
    ('approved_by'), ('approved_at'), ('requested_by'), ('reviewed_by'),
    ('created_at'), ('updated_at')
)
select e.column_name as missing_in_database
from expected e
left join information_schema.columns c
  on c.table_schema = 'public'
 and c.table_name = 'technical_reviews'
 and c.column_name = e.column_name
where c.column_name is null
order by e.column_name;
```


## Cách mở màn hình ngay

Trong lúc chờ An sửa query theo kết quả kiểm tra, sửa tạm code để **không embed `technical_reviews` trong query detail**. Đây là cách cô lập lỗi nhanh nhất: case detail vẫn mở bình thường, còn tab Kỹ thuật sẽ hiển thị trạng thái chưa tải dữ liệu.

```typescript
// Xóa hẳn dòng này khỏi .select(...)
technical_reviews(
  id, case_id, version, approval_status, product_id,
  design_revision_id, material_spec, thickness_mm,
  special_requirements, mold_option, mold_id, pocket_count,
  cutting_die_option, cutting_die_id, machine_id, lead_time_days,
  cycle_time_sec, technical_constraints, rejected_reason,
  approved_by, approved_at, requested_by, reviewed_by,
  created_at, updated_at
),
```

Đồng thời thay phần type/state an toàn:

```typescript
technical_reviews: TechnicalReview[]

// Khi truyền component
reviews={caseData.technical_reviews ?? []}
```

Query còn lại chỉ gồm `business_cases`, `companies`, `employees` và `quotations` — các bảng/FK này đã được xác minh đầy đủ. Khi detail mở được, ta xác nhận 100% lỗi nằm trong danh sách field `technical_reviews`.[^5_3]

## Bổ sung bắt buộc cho An

Trong code hiện tại, An cần log đầy đủ error thay vì nuốt lỗi và chỉ `setLoading(false)`:

```typescript
if (error) {
  console.error('Failed to load business case:', {
    code: error.code,
    message: error.message,
    details: error.details,
    hint: error.hint,
  })
  setLoading(false)
  return
}
```

Supabase khuyến nghị log cả `code`, `message`, `details`, đặc biệt `hint`, thay vì chỉ log một chuỗi, vì `hint` thường chứa hướng dẫn khắc phục trực tiếp từ Postgres.[^5_2]

Anh hãy chạy **query đối chiếu thứ hai** và gửi phần `missing_in_database`; chỉ cần kết quả đó là An có thể sửa đúng cột trong một commit, không cần đoán tiếp.

## 1. Claude Sonnet vs GPT — Mô hình nào phù hợp?

## 2. Luồng nghiệp vụ thực tế sau Báo giá — Xác nhận từ dữ liệu

Anh hoàn toàn đúng — **không thể nhảy thẳng từ Báo giá sang Giao hàng**. Dưới đây là luồng thực tế đã được xác nhận từ cả `comprehensive_system_analysis.md` và cấu trúc Access DB gốc trong `implementation_plan20260701.md` :

```
Báo giá (Quotation)
    ↓ Khách hàng duyệt
Chỉ thị sản xuất / Job (tblJOB → jobs)
    ↓ Chia nhỏ công đoạn
Job Steps / Kỳ hạn gia công (tblKyHanGC → job_steps)
    ↓ Công nhân thực thi
Work Logs / Nhật ký gia công (tblThoiLuongGC → work_logs)
    ↓ Hoàn tất QC / Kiểm tra
Inspection / Kiểm tra chất lượng
    ↓ Đóng gói
Phiếu giao hàng / 納品書 (shipments)
```

**Quan trọng:** Theo Access DB gốc, `Job` chứa cả trường `DeliveryDeadline` (deadline giao hàng) và `MoldShippingDate` (ngày gửi khuôn)  — tức là **giao hàng được quản lý từ trong Job**, không phải là một module độc lập sau Job.
